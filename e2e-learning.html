02一個 Request 的完整旅程

以下用單 GPU、decoder-only、自回歸生成作為基準。多模態、MoE 與 speculative decoding 之後再加。

初始化：先把可重用的工作準備好

讀 model config 與權重，建立 PyTorch model，選算子與 attention backend，配置 workspace 和 KV 資源。 依實際選項執行 warmup、JIT、autotune、compile、Graph capture。這些成本可能發生在不同階段，不能全算成一次「編譯」。 入口：model_loader.py、model_engine.py。

接收：文字變成 Request

API 接收 prompt 與 sampling 設定，輸入處理得到 token IDs，request 保存生成狀態與限制。 Streaming 決定回應的交付方式，與模型每輪如何計算是相關但不同的介面。 入口：BaseLLM.generate / generate_async、LlmRequest。

選工作：Scheduler 決定這輪執行誰

檢查 request 是否能容納、token budget 與 KV 資源，再組成本輪 batch。 這個 batch 可能是 prefill、decode 或 mixed；request 數量、query token 數量、KV 長度不是同一個數字。 入口：PyExecutor._schedule、scheduler.py。

做運算：Model Engine 執行一次 Forward

準備張量與 metadata，選 eager、compiled callable、Graph replay 或相容的分段路徑。 Transformer 各層進行 norm、QKV projection、position encoding、attention、output projection 與 MLP。 使用哪個 kernel 由模型、dtype、shape、GPU、quantization 與設定共同決定。 入口：PyTorchModelEngine.forward、modeling_llama.py。

選 Token：Logits 變成生成結果

logits 經過必要的 penalties、temperature、篩選與 sampling；結果更新 request state。 未完成的 request 留待下一輪，完成或取消的 request 依實作流程釋放資源並交付回應。 入口：sampler.py、sampler/ops/flashinfer.py。

03三條流程同時存在
服務流程：Request → Scheduler → KV resources → Model forward → Sampling → Response
                                        ↑ 每個 iteration 的交界
編譯流程：Python → Dynamo / guards → 圖轉換 → backend / Inductor → generated / external kernels
                                        ↓ 可供執行的 callable
執行流程：metadata 更新 → eager launch / CUDA Graph replay → GPU 完成 → 更新 request

這些是概念與責任分工，不保證每一條邊都是直接函式呼叫。 編譯不是每個 request 都從零做；Graph replay 仍需要有效資料、metadata 與資源生命週期。

都叫 scheduler / plan 管理的對象 例子
Serving scheduler request 與 token budget 誰進 batch、長 prompt 切多少
Compiler scheduler 圖節點、迴圈、資料依賴 哪些運算能融合、先後順序
FlashInfer planning attention 工作切分與相關 metadata page tables、head dims、workspace
GPU hardware scheduling blocks、warps、SM 執行資源 哪些 block/warp 可被排上硬體

04第 01 集主題：為什麼要算子融合

問題： GPU 做很簡單的逐元素運算時，算術可能不是主要成本。

以 square(relu(x)) 為例，eager 可能先產生 ReLU intermediate，再執行平方。 若兩次各讀寫全部 FP16 元素，理想化 tensor traffic 為每元素 8 bytes；融合成一次讀、一次寫則為 4 bytes。 這是 tensor 讀寫量模型，不是實測 HBM traffic，也不包含 allocator、cache 或其他成本。

融合可省 intermediate 的讀寫與部分 launch 成本，但可能增加 register pressure、編譯時間或限制其他重用。 小 workload 可能偏 launch-bound，大 workload 可能偏 bandwidth-bound；不能把標題的「99%」套用所有情境。

Repo： fused_relu2_triton.py 第 26 行的 _relu2_kernel。 這是手寫 Triton 融合案例，不是已證明由 Inductor 自動產生的輸出。

練習： 畫 eager 與 fused 版本每次 load/store；列出 dtype、NaN 與 aliasing 需要核對的條件。

05第 02 集主題：Dynamo 如何抓圖

問題： 編譯器如何從動態 Python 程式看見可優化的 tensor 運算？

Dynamo 透過 Python frame/bytecode 層的分析，將可處理的 PyTorch 操作整理成 FX graph，交給可替換 backend。 FakeTensor 可以攜帶 shape、dtype、stride 等資訊，而不執行對應的大型真實 tensor 計算。 不代表原始 Python 的任何副作用都不執行，也不代表第一次呼叫完全沒有真實運算。

無法納入的部分可能產生 graph break；在要求 fullgraph 的情況，這可能直接成為錯誤，而不是默默切圖。 資料值控制的 Python branching 與只依 shape 決定的分支，也要分開分析。 Dynamo 官方說明。

Repo： model_engine.py 第 490 行建立自訂 Backend，511 行附近傳給 torch.compile。 這是條件式路徑，要先讀第 434 行附近的 compile 設定與 model 分支。

練習： 用紙筆畫 relu(x + y) 的 FX 概念圖，區分 tensor metadata 與 tensor 內容。

06第 03 集主題：Guards 與動態形狀

問題： 同一份 compiled code 何時可以安全重用？

Guard 是編譯假設的檢查，例如 dtype、shape/stride、Python 值或 module state。 有符合的已編譯變體就重用；沒有時可能觸發 tracing/compilation，達到限制後的行為取決於版本與設定。 Graph break 是圖擷取的邊界；guard failure 是某份已編譯變體的假設不成立，兩者不是同義詞。

符號維度可讓一份程式支援多種尺寸，但不會消除所有假設與分支 specialization。 因此「換十種形狀只編譯兩次」要有實際程式與 logs 才能重現，不能視為固定規則。 Guards 與 runtime overhead。

Repo： Backend.call 第 187 行，讀取 FakeTensor 中的 token 維度以銜接 piecewise 邏輯。 TRT-LLM compile graph 可支援哪些 shape，與它 capture 了哪些 CUDA Graph buckets，是兩個問題。

練習： 預測只改內容、改 shape、改 dtype、改 stride，各可能使哪種假設失效；再用 logs 驗證。

07第 04 集主題：AOTAutograd 為什麼出現在這裡

問題： 訓練時 forward/backward 如何一起被整理？推論又為何見到這個名字？

訓練需要 backward，編譯流程可分析 forward 保存哪些值、哪些值重算，權衡運算與記憶體。 這是 compiler 的圖轉換階段，不代表 Python model 需要改成另一種訓練框架。

推論沒有梯度需求時，不應因此虛構 backward 計算；但框架仍可能重用這一層的圖整理與 decomposition infrastructure。 本 checkout 的直接證據： backend.py 第 222 行呼叫 aot_module_simplified(..., fw_compiler=self.optimize, decompositions=select_decomp_table())。

練習： 沿這個呼叫找 fw_compiler 實際是哪個函式；說明為何看到 aot_autograd import 不足以證明 inference 執行 backward。

08第 05 集主題：Decomposition 與 Functionalization

問題： 編譯器如何支援大量高階算子，以及有原地修改的程式？

Decomposition 把選定高階操作轉成較基礎的操作組合，減少後端需要獨立支援的語意。 Functionalization 用較容易分析的形式表達 mutation 與 aliasing，讓資料相依關係清楚。 這不是允許忽略副作用；正確性要求觀察到的結果與原程式契約相符。

若張量共享 storage，x.add_() 的影響可能透過另一個 view 被觀察到。 因此不能單純把所有 inplace 換成 out-of-place 就宣布等價。

Repo： remove_copy_pass.py 與 Backend.optimize 的 remove_copy_for_mutates_args。 這是 checkout 中與 mutation/copy 優化相關的入口；不是宣稱它完整實作 PyTorch functionalization。

練習： 畫一個 tensor 與其 view，說明原地更新如何影響另一個參照。

09第 06 集主題：Inductor IR 與中間值

問題： 圖裡的每個節點，是否都需要一份獨立的 GPU buffer？

IR 是編譯器保存計算意義的中間表示。對逐元素組合，編譯器可以表達「輸出索引 i 的值怎樣由輸入算出」。 如果相鄰運算適合融合，中間值可留在 kernel 內，不必都 materialize 成顯存張量。 但 reduction、外部 library 呼叫、跨節點重用與 layout 要求，可能使 intermediate 仍需要實體 storage。

FX graph、ATen graph、Inductor IR 與最後生成的 kernel code 處於不同層次，不能當成同一張圖。 看 graph 節點數量也不能直接推算 kernel launch 次數。

Repo： backend.py 第 183 行的 compile_fx_inner； piecewise_optimizer.py 的 compile_fx。 它們是進入 Inductor 的接點；Inductor 本體在 PyTorch dependency，不在 TRT-LLM 這兩個檔案裡。

練習： 對同一段小函式分別列出 Python operations、概念圖節點與預期 kernel 邊界，最後查看 generated code 核對。

10第 07 集主題：Compiler Scheduling 與融合限制

問題： 兩個相鄰算子，什麼時候能放進同一個 kernel？

編譯器必須考慮 read/write dependencies、shape、layout、同步與成本。 producer-consumer fusion 可能省 memory traffic；獨立運算也可能共享一次 launch。 但多 consumer、reduction、register 使用量、外部算子邊界與不同 parallelization 可能阻止或降低融合收益。

正確性先於效能：例如一個寫入會影響另一個讀取，改變順序就可能改變結果。 「能融合」與「融合後更快」是不同判斷。

Repo： patterns/residual_add_norm.py 及 Backend.build_custom_passes：自訂 pattern 把特定模式換成融合操作。 這與 Inductor 自己的 scheduler 是相鄰層次，不能認為這個 pass manager 就是完整 Inductor scheduler。

練習： 找出 pattern 的匹配條件；推理為什麼 quantized 與非 quantized 路徑不能只改函式名稱。

11第 08 集主題：Triton 的 Program 與 Block

問題： 怎麼用 Python 形式描述 GPU 上一批資料的運算？

一個 Triton program 處理一個資料區塊，program_id 決定區塊位置，arange 建立區塊內的索引，mask 保護尾端。 Triton 的邏輯元素區塊不是「一個元素對一個 CUDA thread」的固定映射；實際分配由編譯器與配置決定。 BLOCK=4096 不代表一個 CUDA block 啟動 4096 threads。 Triton 官方入門。

Repo： _relu2_kernel 使用 tl.load → fp32 計算 → cast → tl.store，有明確 NaN propagation。 外層 fused_relu2 還檢查 output layout 與 partial overlap，這些屬於 operator correctness，不能只讀五行 kernel 就略過。

練習： 設 n=10、BLOCK=4，列出三個 programs 的索引與 mask。這是教學參數，不是 repo 的固定 launch 配置。

13第 10 集主題：GEMM Templates 與 Autotune

問題： 矩陣乘法明明公式相同，為什麼有不同 kernel？

C[M,N] = A[M,K] × B[K,N] 的 M/N/K、dtype、layout、scales 與 GPU 會影響最佳 tile、pipeline 與實作。 Autotune 在候選中量測或使用策略挑選，並付出搜尋、編譯、workspace 與記錄成本。 它不是數學上保證全域最佳，也不一定每次 forward 重跑搜尋。

Tensor Core 可加速支援格式的矩陣運算，但小 shape、低重用、layout 轉換或其他 overhead 仍可能主導。 GEMM 的 arithmetic intensity 要把實際 bytes 與 reuse 算進去，不只看 FLOPs。

Repo： linear.py 第 585、662 行附近的 cuBLAS 分支， 以及 autotuner.py。這兩個入口不代表所有 Linear 都共用同一套 autotune。

練習： 為小 batch decode 與大 prefill 列出不同的 M，推理同一 tactic 為什麼可能不適用。

14第 11 集主題：CUDA Graphs 省掉什麼

問題： 每輪 decode 重複提交很多小 GPU 工作，CPU 提交成本能否降低？

Graph capture 記錄可重播的 GPU 工作與 dependencies；replay 降低 host 端逐項提交成本。 GPU 仍要執行那些運算，不會因 replay 就免除 memory traffic 或把所有 kernel 變成一個。 kernel fusion、Graph replay 與 overlap 分別處理不同成本，可以共存。

普通 capture/replay 需要滿足對執行結構、storage 位址與操作相容性的要求。 更新同一 storage 的資料值，與每次重新配置 tensor 並換掉 pointer，是不同操作。 若修改 graph 參數或使用其他進階更新機制，必須有相應 API 與限制，不能假設一般 replay 會自動接受。 PyTorch CUDA Graph 語意。

Repo： CUDAGraphRunner.capture / replay 第 686、789 行。 PiecewiseRunner.call 第 199 行會記錄 input addresses、warmup、capture，再 replay。

練習： 畫出「持久 input buffer → 寫入新資料 → replay」；標出哪個 owner 必須保證 storage 仍存活。這就接回 M01。

18FlashInfer 的 Plan / Run 與 Paged KV

架構位置： request scheduler 已選好工作與 KV 資源，attention adapter 將它們轉成 kernel 能理解的 metadata。

用兩個 Requests 手算一次

假設每頁 16 tokens，A 的有效 KV 長度為 38，B 為 9。以下是示意 page-list 格式，不是所有 TRT-LLM backend 的實體配置。

request             A                 B
logical pages       0, 1, 2           0
physical page IDs   7, 2, 9           5
indptr              [0, 3, 4]
indices             [7, 2, 9, 5]
last_page_len       [6, 9]
length              2×16+6 = 38       0×16+9 = 9

indptr 把扁平 page list 分給每筆 request；indices 指向實體頁；尾頁長度防止讀到無效位置。 若每筆 query 長度為一，普通 decode 的 Q 可概念化為 [2,Hq,D]；prefill 則可能有 ragged query offsets。 Hq 不一定等於 Hkv，GQA 的 mapping 必須正確。

19Custom Op 與 Fake Implementation：如何接上編譯器

問題： 外部高效 kernel 不能被 Python tracing 完整看穿，怎麼放進模型圖？

Custom op 提供可辨識的 operator 邊界。Fake implementation 提供編譯期所需的輸出 metadata， 不是偷偷在 CPU 上算一遍 attention，也不是「假結果可以拿來 sampling」。 mutation schema、aliasing 與 output shape/dtype 必須和真實行為一致。

本地例子： flashinfer_custom_ops.py 第 16 行：

@torch.library.custom_op("trtllm::flashinfer_silu_and_mul", mutates_args=())
def flashinfer_silu_and_mul(x: torch.Tensor) -> torch.Tensor:
    return silu_and_mul(x, enable_pdl=get_env_enable_pdl())

其 register_fake 回傳對應一半最後維度的 metadata。這反映 gated activation 的輸出契約，不能直接套到任意算子。 flashinfer_fused_add_rmsnorm 則宣告修改 input 與 residual，與無 mutation 的 activation 不同。

Opaque custom op 可讓 compiler 保留這個節點，但一般不能任意跨越邊界分析或融合其內部。 因此可搭配 pattern pass，或由 library 直接提供 fused operator。 PyTorch Custom Operators。

檢查： 如果 fake implementation 的輸出 shape 正確，但 mutation 宣告錯誤，為什麼程式仍可能算錯？

20Piecewise CUDA Graph：編譯與 Library 的接縫

問題： 模型大部分可重播，但某些 attention planning 或 metadata 行為需要每輪處理，怎麼辦？

Piecewise 思路是保留需要 runtime 處理的邊界，將相容區段 capture/replay。 在本 checkout 的實作中，_piecewise_boundary_ops 列出 attention、MLA、GDN、Mamba 等可選 custom op 邊界。 不能推論「所有 attention 永遠不可 capture」，因為普通 generation graphs 與其他 backends 可能支援不同方式。

本地概念路徑：

torch.compile → TRT-LLM Backend → AOT 圖整理與 patterns
              → 依 boundary ops 切段
              → supported segment: compile / warmup / capture / replay
              → excluded boundary: 對應 eager/custom op callable

PiecewiseInterpreter / PiecewiseRunner 會維護 entries、capture 狀態與 storage 位址。 PiecewiseRunner.__call__ 不符合 entry 或 flags 時會走 default_callable，不是無條件 replay。

本 checkout 文件也有不透過 torch.compile 的實驗性 breakable prefill graph 路徑。 它與 piecewise 是不同選項，支援限制要查文件，不能把「不用 compile」說成「不用 Graph」。 本地 compile / prefill graph 文件。

26FlashAttention、PagedAttention 與 FlashInfer 的關係

先回到公式： 對一個 query head，attention 是 softmax(QKᵀ / sqrt(D) + mask) V。 Q 的 query 長度和 K/V 的歷史長度可不同；GQA 還涉及 query heads 到 KV heads 的對應。

FlashAttention：改變資料搬運與計算安排

直接實作可能保存整份 query×key score/probability 矩陣。 FlashAttention 以 tiles 計算，配合 online softmax 維護局部統計與輸出，減少顯存往返與大型中間矩陣。 它仍依 exact attention 語意處理資料；dense prefill 的主要計算複雜度不會因此從二次自動變線性。 浮點運算順序不同，結果不保證 bitwise 一致。 FlashAttention 原始論文。

單一 query row 的教學遞迴如下。新 tile 的 scores 已包含 scaling/mask，舊狀態為 max m、分母 l、未正規化向量 o：

m_new = max(m, max(scores_tile))
alpha = exp(m - m_new)
p     = exp(scores_tile - m_new)
l_new = alpha * l + sum(p)
o_new = alpha * o + p @ V_tile
最後 output = o / l

這不是完整 kernel：還要處理初始值、完全 masked rows、GQA、並行歸約、dtype 與記憶體配置。 重點是：改變目前 max 時，用同一比例重縮舊累積值，因此不需要保留所有舊 scores。

PagedAttention：改變 KV 的配置與尋址

KV 以 blocks/pages 管理，透過邏輯到實體映射存取；可降低配置碎片並支援相應的 reuse 策略。 它不會讓有效 KV tokens 的元素數憑空變少，也不等於 attention softmax 被近似。 對應 本 repo KV cache 文件 與第 18 節的 page list。

FlashInfer：提供與整合這些需求相關的 Operators

Library 必須把不同 KV layout、變動長度、query 形狀與 GPU 特性轉成可執行的計畫。 這就是第 18 節的 metadata、plan/run 與不同 backend 存在的原因。 FlashInfer 論文討論 KV 格式、JIT 客製化與動態負載下的排程及 Graph 相容性； paper 數據不當作目前本機或 TRT-LLM 版本的 benchmark。 FlashInfer 論文。

檢查： 可以同時使用 paged KV 與 IO-aware tiled attention 嗎？它們各改變什麼？

這是手算模型，不是某個已執行的 checkpoint：32 layers、Hq=32、Hkv=8、D=128、KV 為 BF16， 單 GPU、無 prefix sharing、無特殊壓縮或輔助 cache。A prompt 38 tokens，B prompt 9 tokens，每頁 16 tokens。

Prefill：一次處理已知的 Prompt

以 packed tokens 表示時，本輪共 47 個 query tokens。隱藏維度示意為 4096， Q 可視為 [47,32,128]，新 K/V 各為 [47,8,128]；具體 forward 輸入與 layout 要核對模型。 A 和 B 各自套用正確的 causal 邊界，不能把 packed storage 當作一條 47-token 序列互相注意。

每 layer 的有效 KV bytes：

2 × 47 × 8 × 128 × 2 = 192,512 bytes = 188 KiB

頁數為 A 三頁、B 一頁；若以完整四頁保留空間，則每 layer 是：

2 × (4 × 16) × 8 × 128 × 2 = 262,144 bytes = 256 KiB
32 layers 合計 8 MiB

未包含 metadata、workspace、allocator 預留與其他模型資源；與「有效 KV 元素數」分開計算。

First Sampling：預測第一個新 Token

普通生成可從各 request 最後有效 prompt 位置的 logits 產生第一個新 token。 這時 KV cache 包含 prompt；剛 sample 出的新 token 還沒有因為 sampling 自動生成 K/V。 產生 token 的數學操作，與對該 token 執行下一次 model forward，是不同步驟。

Decode：把剛生成的 Token 當下一輪輸入

假設兩筆都沒結束，下一輪各輸入一個 token，Q 共兩列。 本次 forward 為這兩個新輸入產生 K/V；各 request 的有效 KV 長度由 38/9 增至 39/10， attention 讀取各自歷史並產生下一個位置的 logits，再做 sampling。 具體 cache write 與 attention kernel 的融合方式、執行順序由 backend 決定。

普通單 token decode 的 attention 會讀歷史 KV；整個模型仍包含 projection、MLP 等運算。 小 batch 時 weights/KV traffic 或 launch overhead 常重要，但大 batch、長 context、量化與不同硬體可改變瓶頸。 不能把「decode 常 memory-bound」當作所有 kernel 的固定結論。

完成、取消與 Reuse

若 B sample 到 EOS 或符合停止條件，它不再需要為該完成狀態執行下一輪普通 decode。 runtime 要處理 pending GPU work、回應狀態與 KV 釋放／reuse 政策。 釋放邏輯 ownership 不能造成仍在使用的實體頁被過早分配給新 request。

檢查： 第一個新 token 已經回應給使用者，為什麼它的 K/V 可能尚未在 cache 裡？

28擴展到多 GPU：哪幾層開始改變

先保持前面的 request 主線，再加入以下變化；不要一次把所有平行方式當作同一種切模型。

方式 主要切分對象 往端到端流程增加的問題
Tensor Parallelism（TP） 一層內的 tensor／計算 head/weight 分片、collectives、KV 分布、通訊與算子的融合
Pipeline Parallelism（PP） 模型 layers / stages activation 傳遞、microbatches、stage scheduling 與空泡
Expert Parallelism（EP） MoE experts token routing、dispatch/combine、負載與通訊
Prefill/Decode 分離 request 的不同執行階段 KV transfer、交接狀態、排隊與不同 GPU 資源配置

NCCL 提供 GPU 通訊 primitives；NIXL 在本 repo 的 disaggregated serving 可參與 KV transfer。 這些元件不代替 tokenizer、model 或 FlashInfer attention operator；它們提供不同的系統能力。 通訊本身可能涉及 kernel、stream、workspace 與 capture 相容性，因此也要接回 M01/M06。

閱讀順序：parallel strategy → MoE guide → disaggregated serving。 在選定配置下追一次實際 communicator 與 cache transceiver，再量測 compute / communication / overlap。
